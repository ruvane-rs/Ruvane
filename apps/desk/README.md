# Ruvane Desk · alpha.61

A local ticket application generated by the Ruvane CLI, then implemented using
public framework APIs. Everything is written in English. There are no third-party
Cargo or npm dependencies.

One project, **Ruvane**, has up to 128 tickets. Each ticket has a title, description,
state (`Open`, `In progress`, `Closed`) and monotonically increasing revision.
The application has a paginated list, creation and detail/edit screens, server
rendering, Rust/Wasm controls and native HTML form fallbacks.

## Run

From the repository root:

```sh
cargo build --offline --locked --bin ruvane
cd apps/desk
../../target/debug/ruvane dev --offline
```

Open the printed loopback address and choose **Open local session**. This creates
a local capability cookie, not a verified user account. The pilot has no passwords,
TLS, public deployment, roles, multiple workspaces or attachments. Sessions are
memory-only and expire on restart. Ticket data is retained.

For a standalone bundle, run in this directory:

```sh
../../target/debug/ruvane build --offline
./dist/build-000001/ruvane-app --port 3000
```

Use the actual build directory printed by the CLI. The native executable embeds
its Wasm, CSS and browser modules. It runs without application sources. Build and
asset-export commands never open business storage. Runtime ABI 15/RVN9, 22 numeric
exports and four core assets are unchanged.

By default, data is written to `desk-data/` under the server's working directory.
To keep one location across development runs and standalone bundles, set
`RUVANE_DESK_DATA` to an **absolute path** with an existing, trusted parent. On
macOS/Linux this must resolve through real directories without symlinks. The
application creates the final directory with mode 0700 and files with mode 0600.
The current disk adapter supports Unix; it fails closed elsewhere.

Add `?native=yes` to `/tickets`, `/tickets/new` or a ticket detail URL for a
script-blocked document. Native forms carry a CSRF token and, when editing, the
exact version that was loaded. Successful forms use POST/303. Invalid or stale
submissions retain their fields on the returned page. Single-line control
characters and fields beyond the framework's form limits are rejected before
rendering a draft.

## Safe editing

Title: 1–120 UTF-8 bytes, nonblank, no controls. Description: 0–1024 UTF-8 bytes,
with LF and tabs allowed. Wire states: `open`, `in_progress`, `closed`. The Wasm
state button changes the draft; **Save ticket** persists all three fields.

Private pages, navigation seeds and API results are no-store. Ticket mutations check
same origin, session, CSRF and a per-session quota before reaching the store.
PATCH uses a retained strong `If-Match` tag. The version comparison and durable
publication share one mutex. A stale writer receives 412; missing or wildcard
preconditions receive 428. Restart creates a new tag namespace, preventing stale
open tabs from writing into a new server lifecycle.

When another tab wins, the losing editor keeps its draft and blocks saving.
**Replace draft with current ticket** is an explicit, destructive replacement of
the local draft. Native error pages also keep the submitted draft and link to the
current saved record. Navigating away discards a draft; drafts are not stored in
browser storage.

Creation is **not idempotent**. If a reply is lost, a ticket may already be saved.
The Wasm editor keeps its draft, blocks another save and never replays the POST.
Inspect the list before explicitly discarding the uncertain draft. Native error
responses similarly require inspection before resubmission. Closing a tab during
a request can leave its outcome unknown; inspect saved data after returning.

## Storage and recovery

The application owns its bounded `RDS1` ticket snapshot. It uses std file I/O,
exclusive writer files and a process-local lease; no database crate or framework
private module is imported. Each publication writes a fresh `next.bin`, syncs it,
renames it over `store.bin`, then syncs the directory. CRC32 detects accidental
corruption; it does not authenticate files or encrypt data. The local OS account
and the data directory's parent must be trusted. Backups require the server to
be stopped.

A normal shutdown removes `LOCK`. A crash or failed publication preserves recovery
artifacts and blocks normal startup. Stop **all** writers before running:

```sh
./dist/build-000001/ruvane-app --recover /absolute/path/to/desk-data
```

Recovery validates the committed snapshot before removing an interrupted lock or
temporary file. It starts no server and does not overwrite corrupt committed data.
After an uncertain write, the recovered snapshot may contain either the old or
new record; inspect it before writing again. Recovery is an offline operator
command, never an HTTP endpoint. It cannot determine whether another process is
using the directory: ensuring all writers are stopped is the operator's duty.
Partial initialization and invalid permissions/foreign files are refused for
manual inspection. There is no automatic reset or schema downgrade.

## Layout and checks

- `src/model.rs`: shared validation, ticket DTOs and bounded seeds.
- `src/components.rs`: list and editor; conflict/uncertainty handling.
- `src/pages.rs`: page registry and generic shell.
- `src/native.rs`: sessions, guards, JSON endpoints and native forms.
- `src/native/store/`: first-party snapshot adapter and failure tests.
- `src/main.rs`: CLI protocols and native startup/shutdown.
- `browser/`: application-owned Wasm export entry point.

This is a separate Cargo workspace. Its dependency graph has four local packages:
the Desk library and Wasm entry point, plus Ruvane's two framework packages.
`python3 tools/check_first_party.py` from the repository root audits both graphs.
Run `tools/check_desk.sh` from the repository root for native checks and the
source-hidden bundle/HTTP/Wasm suite. The actual
browser fixture is launched separately via `browser/tests/desk-browser.mjs` in
the test-only bundle; it is not shipped by the application.

Alpha.61 establishes this vertical slice. Workspace roles and attachments belong
to alpha.62; richer daily workflow and broader stabilization follow separately.
